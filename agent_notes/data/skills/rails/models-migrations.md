## File Structure

Migrations live in `db/migrate/` with timestamped filenames. A sample of Fizzy's (abridged):

```
db/migrate/
├── 20251111122540_initial_schema.rb
├── 20251120194700_remove_all_foreign_key_constraints.rb
├── 20260209165805_notifications_data_migration.rb
└── 20260828120000_create_identity_transfers.rb
```

Filenames are generated by Rails (`bin/rails generate migration name`). Each migration is a one-time change applied in timestamp order. Fizzy also keeps a MySQL schema (`db/schema.rb`) and a SQLite schema (`db/schema_sqlite.rb`).

Why: timestamps give a total order, so a fresh machine replays the history the same way every time (Fizzy: `db/migrate`).

## Basic Patterns

### Create a table with a UUID key and timestamps

```ruby
# db/migrate/20260828120000_create_identity_transfers.rb
class CreateIdentityTransfers < ActiveRecord::Migration[8.2]
  def change
    create_table :identity_transfers, id: :uuid do |t|
      t.uuid :identity_id, null: false
      t.string :token, null: false

      t.timestamps

      t.index :identity_id
      t.index :token, unique: true
    end
  end
end
```

Indexes can be declared inside the `create_table` block (as here) or separately with `add_index`.

Why: declaring the indexes in the block creates them together with the table (Fizzy: `db/migrate/20260828120000_create_identity_transfers.rb`).

### Alter a table: add columns and indexes

```ruby
# db/migrate/20251111153019_add_number_to_cards.rb
class AddNumberToCards < ActiveRecord::Migration[8.2]
  def change
    add_column :cards, :number, :bigint, null: false
    add_column :accounts, :cards_count, :bigint, default: 0, null: false
    add_index :cards, [:account_id, :number], unique: true
  end
end
```

Use `change` when Rails can reverse the operation (`add_column`, `add_index`). Use `up` and `down` when it cannot; see Reversible Migrations below.

Why: a `change` migration rolls back without extra code (Fizzy: `db/migrate/20251111153019_add_number_to_cards.rb`).

## Indexes

### Composite indexes lead with the tenant

```ruby
# db/migrate/20260709120000_add_account_board_status_index_to_cards.rb
class AddAccountBoardStatusIndexToCards < ActiveRecord::Migration[8.2]
  def change
    add_index :cards, [ :account_id, :board_id, :status ]
  end
end
```

Tenant tables lead their composite indexes with `account_id`, as the `cards` indexes in `db/schema.rb` do (`[account_id, board_id, status]`, `[account_id, last_active_at, status]`, `[account_id, number]`).

Why: a query filtered by account first can ride the index, as the comment on `Card.auto_postpone_all_due` explains (Fizzy: `app/models/card/entropic.rb`).

### Partial indexes

Fizzy supports both MySQL and SQLite from one `db/migrate` directory, and that directory contains no partial index (`add_index ... where:`). MySQL has no partial indexes.

Why: a migration that has to work on both databases uses plain and composite indexes (Fizzy: `db/migrate`, `db/schema_sqlite.rb`).

## Foreign Keys

Fizzy has no foreign-key constraints. One migration removes them all, and `db/schema.rb` contains no `add_foreign_key`:

```ruby
# db/migrate/20251120194700_remove_all_foreign_key_constraints.rb
class RemoveAllForeignKeyConstraints < ActiveRecord::Migration[8.2]
  def change
    remove_foreign_key "active_storage_attachments", "active_storage_blobs", column: "blob_id" rescue nil
    remove_foreign_key "active_storage_variant_records", "active_storage_blobs", column: "blob_id" rescue nil
    remove_foreign_key "board_publications", "boards" rescue nil
# ...
  end
end
```

The commit that introduced the change (6e67a7787) explains the choice:

> These have been a contributing cause to some deadlocks, but also this makes some operational tasks harder (data loading, data truncation) and has some performance impact on insert/update/delete operations. The team consensus is that we aren't relying on them, and so we're comfortable with the referential integrity risk.

Without constraints, the database does not stop an orphaned row, so declare `dependent:` on the association and add an index for each `*_id` column you query.

Why: constraints contributed to deadlocks and made data loading and truncation harder (Fizzy: `db/migrate/20251120194700_remove_all_foreign_key_constraints.rb`, commit 6e67a7787).

## Data Migrations

When a migration changes data, define a small stub model inside it so it does not depend on the application model, which may change later:

```ruby
# db/migrate/20260209165805_notifications_data_migration.rb
class NotificationsDataMigration < ActiveRecord::Migration[8.2]
  BATCH_SIZE = 10_000

  class Notification < ActiveRecord::Base
    self.table_name = "notifications"
  end
# ...
  def change
    reversible do |dir|
      dir.up do
        populate_card_id
        collapse_duplicates
      end
    end
# ...
  end
```

The constant `BATCH_SIZE` is set once on the migration class and read inside the helper methods (`LIMIT #{BATCH_SIZE}` in `collapse_duplicates`). `reversible` with only a `dir.up` block runs the data change forward and does nothing on rollback.

Why: the stub pins the table name and nothing else, so the migration keeps working after `Notification` changes (Fizzy: `db/migrate/20260209165805_notifications_data_migration.rb`).

## Reversible Migrations

Most migrations are reversible through `change`. When Rails cannot invert the operation, write `up` and `down`:

```ruby
# db/migrate/20251219120755_drop_card_engagements.rb
class DropCardEngagements < ActiveRecord::Migration[8.2]
  def up
    drop_table :card_engagements
  end

  def down
    create_table :card_engagements, id: :uuid do |t|
      t.references :account, type: :uuid, null: false
      t.references :card, type: :uuid, null: false, index: true
      t.string :status, null: false
      t.timestamps
    end

    add_index :card_engagements, [ :account_id, :status ]
  end
end
```

`down` recreates the table, so the migration can still be rolled back. For a single step inside `change`, wrap the forward and backward halves in `reversible do |dir|`.

Why: a migration that can be rolled back makes a bad deploy recoverable (https://guides.rubyonrails.org/active_record_migrations.html#using-the-up-down-methods).

## Best Practices

### Index what you query

Index the `*_id` columns that queries use, composite keys for scoped queries (`account_id` plus the filter column), and columns used in `where` or `order`. The `cards` table shows the shape:

```ruby
# db/schema.rb
create_table "cards", id: :uuid, charset: "utf8mb4", collation: "utf8mb4_0900_ai_ci", force: :cascade do |t|
  t.uuid "account_id", null: false
  t.uuid "board_id", null: false
  t.uuid "column_id"
# ...
  t.bigint "number", null: false
  t.string "status", default: "drafted", null: false
# ...
  t.index ["account_id", "board_id", "status"], name: "index_cards_on_account_id_and_board_id_and_status"
  t.index ["account_id", "last_active_at", "status"], name: "index_cards_on_account_id_and_last_active_at_and_status"
  t.index ["account_id", "number"], name: "index_cards_on_account_id_and_number", unique: true
  t.index ["board_id"], name: "index_cards_on_board_id"
  t.index ["column_id"], name: "index_cards_on_column_id"
end
```

Why: each `*_id` column that queries use gets its own explicit index, as `board_id` and `column_id` do on `cards` (Fizzy: `db/schema.rb`).

### Null constraints

Add `null: false` to a column unless it can legitimately be absent. In the `cards` table above, `column_id` is nullable (`Card#handle_board_change` runs `update! column: nil`) while `account_id`, `board_id`, `number` and `status` are not.

Why: nullability should be a decision, and `NOT NULL` is enforced by the database even when application validations are skipped (Fizzy: `db/schema.rb`).

### Don't edit old migrations

Never modify a migration that has been deployed or run on another machine. Fix it with a new migration. Fizzy brought back a unique index on the publication lookup column with a new migration instead of editing the earlier one:

```ruby
# db/migrate/20260218120000_restore_unique_index_on_board_publication_key.rb
class RestoreUniqueIndexOnBoardPublicationKey < ActiveRecord::Migration[8.2]
  def change
    add_index :board_publications, :key, unique: true
    add_index :board_publications, :account_id
    remove_index :board_publications, [:account_id, :key]
  end
end
```

Why: a migration that has already run elsewhere would not run again, so editing it leaves databases out of sync (Fizzy: `db/migrate/20260218120000_restore_unique_index_on_board_publication_key.rb`).

### Column and table removal

Fizzy removes tables directly in one migration, with a `down` that recreates them (see `DropCardEngagements` above). Whether a deprecation cycle is needed depends on your deploy practice: if you deploy frequently and own the database, direct removal is fine; if other code reads the schema, deprecate first.

Why: the schema is owned by the app, so no second consumer needs a transition period (Fizzy: `db/migrate/20251219120755_drop_card_engagements.rb`).
